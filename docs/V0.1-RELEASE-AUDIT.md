## CLI contract audit

The final v0.1 command grammar implemented by `crates/pgdumpx-cli/src/main.rs` is:

```text
pgdumpx inspect <FILE>
pgdumpx list <FILE>
pgdumpx extract [--max-decompressed-bytes <N>] <FILE> <SCHEMA.TABLE>
pgdumpx find [--max-rows <N>] [--max-decompressed-bytes <N>] <FILE> <SCHEMA.TABLE> <COLUMN> <VALUE>
```

For table-oriented commands, `SCHEMA.TABLE` contains exactly one ASCII `.` and two non-empty components; SQL identifier quoting/escaping is not a v0.1 CLI feature. `extract` accepts a positive decimal `u64` override and otherwise uses 1,073,741,824 bytes (1 GiB). `find` scan limits are optional and otherwise unlimited.

`extract` streams decompressed selected-entry bytes directly to stdout. Its stdout is binary-safe. A later limit, input, decompression, or destination error cannot roll back bytes already written; the process still exits non-successfully and diagnostics remain on stderr. Consumers must treat exit status, not output length alone, as the completion signal.

`find` accepts schema/table/column/value at the UTF-8 CLI boundary while the Rust API remains byte-oriented. A match writes one normalized COPY-text record and exits 0; a completed no-match scan emits no output and exits 1; usage, I/O, archive, decompression, COPY, encoding, unsupported-representation, unknown-column, or resource errors exit 2 or greater with diagnostics on stderr.

## Compatibility and performance claim audit

`docs/COMPATIBILITY.md` remains the source of truth for fixture-backed compatibility. The audit found no cell that claims more than the committed official fixtures demonstrate. In particular, 1.14/1.15 do not inherit LZ4/Zstandard verification merely because 1.16 supports those backends.

The repository contains a reproducible benchmark harness and methodology, but the README does not publish numeric throughput, latency, memory, or competitor-speedup claims. Therefore no public quantitative performance statement needs to be traced to a particular result file at this stage.

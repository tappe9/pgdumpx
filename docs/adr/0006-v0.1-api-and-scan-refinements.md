# ADR 0006: v0.1 API and scan-work refinements

- Status: Accepted
- Date: 2026-08-19

## Context

A pre-implementation review of the accepted v0.1 design found several places where the intended behavior was clearer than the representative API or CLI contract.

Most importantly:

- `column_index() -> Option<usize>` could not distinguish "valid metadata, unknown column" from "column metadata unavailable";
- per-row limits bounded memory but did not provide a library-level way to bound total decompression/scan work;
- the planned CLI did not expose the project's primary row-aware first-match use case;
- COPY-text support and unsupported INSERT-based table-data representations needed an explicit public contract;
- compatibility targets and verified compatibility needed to be documented separately.

These are refinements of the existing Custom Format, read-only, streaming architecture rather than a change in product direction.

## Decision

### Column metadata state is explicit

Column-aware APIs distinguish valid metadata from unavailable/malformed metadata.

Representative API:

```rust
pub fn columns(&self) -> Result<&[Column], PgDumpError>;

pub fn column_index(
    &self,
    name: &[u8],
) -> Result<Option<usize>, PgDumpError>;
```

Semantics:

```text
Ok(Some(index))  -> layout is valid and the column exists
Ok(None)         -> layout is valid but the requested column does not exist
Err(...)         -> the supported column layout could not be derived
```

Positional row iteration may still be available when the data stream is readable but column metadata is unavailable.

### Scan work has operation-level budgets

Per-item parser limits remain part of `Limits` for metadata and row allocation safety.

Long-running row scans additionally accept an operation-level budget equivalent in purpose to:

```rust
pub struct ScanLimits {
    pub max_rows: Option<u64>,
    pub max_decompressed_bytes: Option<u64>,
}
```

Exact naming and default values may evolve during TDD, but the public design must provide a way to bound total scan/decompression work without requiring callers to reimplement the parser loop.

The normal trusted-file convenience path may use generous defaults. Applications processing hostile or externally supplied dumps can select stricter budgets.

### v0.1 CLI exposes a minimal first-match command

The CLI adds a narrow equality-oriented command equivalent in purpose to:

```text
pgdumpx find <FILE> <SCHEMA.TABLE> <COLUMN> <VALUE>
```

This command demonstrates the core row-aware value proposition without introducing SQL parsing or a general condition DSL.

It uses the same table lookup, streaming decompression, COPY parsing, column metadata, scan limits, and `find_first` path as the library API.

### COPY text is an explicit representation contract

`docs/COPY-TEXT.md` defines that `FieldRef::Bytes` contains logical field bytes after COPY text escape decoding.

Row-aware v0.1 APIs support the normal pg_dump COPY-text representation and explicitly reject unsupported INSERT-based representations such as `--inserts`, `--column-inserts`, and INSERT output produced through `--rows-per-insert`.

Unsupported representations return a typed error rather than being guessed or misparsed as COPY text.

### Compatibility claims are evidence-based

`docs/COMPATIBILITY.md` separates intended v0.1 support from fixture-verified support. No compatibility cell is presented as verified before official pg_dump-generated fixtures and tests demonstrate it.

### v0.1 development is milestone-driven

The feature set remains the same broad v0.1 release goal, but implementation is split into internal milestones so TDD can advance from archive primitives to the row-aware user story without treating the entire release as one unit of work.

## Consequences

### Positive

- column-aware callers can handle missing columns differently from unavailable metadata;
- hostile or unexpectedly large compressed data can be bounded by total scan work as well as per-row allocation;
- the CLI visibly demonstrates pgdumpx's primary differentiator;
- COPY byte semantics are testable independently from archive framing;
- INSERT-based dumps fail explicitly instead of producing confusing COPY errors;
- compatibility documentation cannot accidentally overclaim untested combinations;
- implementation work can be divided into smaller TDD milestones.

### Trade-offs

- column helper signatures are slightly more verbose;
- scan-limit accounting becomes part of the streaming reader/search design;
- the CLI gains one additional command before v0.1;
- compatibility documentation requires ongoing fixture maintenance.

## Supersedes or refines

This ADR refines the representative API and resource-limit details in ADR 0004 and ADR 0005. It does not supersede their core decisions: Custom Format remains the focus, normal rows remain borrowed, matched rows remain owned, and `find_first` remains a sequential streaming scan rather than an indexed lookup.
